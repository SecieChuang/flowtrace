## 2. 什么是 Gunicorn Worker

### 比喻

把后端服务想象成一家餐厅：

- **单 Worker（-w 1）**：餐厅里只有**一个厨师**。所有客人的订单都由这个厨师处理。厨师有自己的记事本（内存缓存），记录了今天算过的菜（日视图数据），下次有客人点同样的菜，直接看记事本，不用重新算。

- **多 Worker（-w 2）**：餐厅里有两个厨师（Worker A 和 Worker B）。客人的订单被**轮流**分给两个厨师。每个厨师都有自己的记事本，互相看不到对方的。

### 技术定义

Gunicorn 是一个 Python WSGI HTTP 服务器。`-w 2` 表示它会启动 **2 个独立的 Python 进程**来处理 HTTP 请求。

- 每个 Worker 是**完全独立的操作系统进程**
- 它们共享同一个 SQLite 数据库文件（磁盘上的数据）
- 但它们**不共享内存**。每个进程有自己的变量、自己的缓存
- Gunicorn 使用**轮询（Round Robin）**把请求分发给各个 Worker

### 单/多 Worker 的区别

| 维度 | 单 Worker (-w 1) | 多 Worker (-w 2+) |
|---|---|---|
| 并发能力 | 同一时间只能处理 1 个请求 | 可同时处理多个请求 |
| 内存占用 | 低 | 高（每个 Worker 一份内存） |
| 缓存一致性 | 天然一致（只有一个缓存） | 需要额外机制保证一致 |
| 适用场景 | 低并发、个人工具 | 高并发、生产服务 |
| 故障隔离 | 单点故障 | 一个 Worker 挂了不影响其他 |

## 3. 根因分析

### 直接原因：缓存 + 多 Worker

`server.py` 里有一个内存缓存机制：

```python
_day_metrics_cache = {}

def _get_day_metrics(db, date_str):
    today = datetime.now().strftime("%Y-%m-%d")
    if date_str != today and date_str in _day_metrics_cache:
        return _day_metrics_cache[date_str]   # ← 读缓存
    result = _build_day_metrics(db, date_str)
    if date_str != today:
        _day_metrics_cache[date_str] = result  # ← 写缓存
    return result
```

**逻辑**：
- 历史日期的数据计算一次后，结果存入 `_day_metrics_cache`
- 下次再请求同一天，直接返回缓存，避免重复计算
- **今天的数据不走缓存**，每次实时计算

**问题触发链**：

1. 容器内有 2 个 Worker（A 和 B），各自有一份 `_day_metrics_cache`
2. 通过 API 给 5月1日补打卡 → 请求被 Worker A 处理
3. Worker A 把数据写入 SQLite，然后清除**自己**的缓存
4. Worker B 完全不知道这件事，它的缓存还是旧的
5. 用户刷新页面 → 请求被 Gunicorn 轮流分发给 A 和 B
6. 分到 A → 返回新数据 ✅
7. 分到 B → 返回旧数据 ❌

### 为什么正常打卡从来没出过问题？

因为**正常打卡都是"今天"发生的**，而今天的数据**永远不走缓存**：

```python
if date_str != today and date_str in _day_metrics_cache:
    return _day_metrics_cache[date_str]   # 今天不进入这个分支
```

所以即使有两个 Worker，"今天"的数据每次都是实时计算的，不存在缓存不一致。

这次是因为给**历史日期**（5月1日）补打卡，才触发了缓存路径，暴露了多 Worker 缓存不一致的问题。

### 5月2日全天在岗的根因

`_build_shift_intervals` 查询前后各一天的打卡记录来构建区间。5月2日的 Worker 查询到了：
- 5月1日 19:15 的上班卡（无下班卡）
- 5月3日 10:29 的上班卡

机制 A（活动推断下班）尝试推断 5月1日 19:15 的下班时间，但首个活动片段在 22:12，间隔 177 分钟 > 60 分钟阈值，推断失败。fallback 逻辑直接把区间延伸到下一个上班卡的时间点（5月3日 10:29），产生了跨天区间 `(5月1日19:15 → 5月3日10:29)`。

这个区间被 clip 到 5月2日后，变成了全天 `(0, 1440)`，所以 5月2日显示为全天在岗。

**注意**：5月3日的显示是正常的，因为 5月3日的查询范围是 `5月2日~5月4日`，不包含 5月1日的打卡，所以看不到那个跨天区间。

## 5. 解决方案

### 立即恢复（无需改代码）

**重启 Docker 容器**：
```bash
docker restart flowtrace-server
# 或
docker-compose restart flowtrace
```

重启后：
- 两个 Worker 重新启动，缓存全部清空
- 重新加载数据库时，都会读到新的打卡记录
- 5月1日显示正常，5月2日也恢复正常

### 长期避免（需要改代码）

**方案A：改为单 Worker（推荐）**

修改 `server/Dockerfile`：
```dockerfile
# 原命令
CMD ["gunicorn", "-w", "2", "-b", "0.0.0.0:8000", "--timeout", "30", "server:app"]

# 改为
CMD ["gunicorn", "-w", "1", "-b", "0.0.0.0:8000", "--timeout", "30", "server:app"]
```

理由：
- 这是个人工具，并发极低，单 Worker 完全够用
- 彻底消除多进程缓存不一致问题
- 改动最小，风险最低

**方案B：去掉缓存**

删除或注释掉 `_day_metrics_cache` 相关逻辑。历史日期的计算量不大，去掉缓存对性能影响可以忽略。

**方案C：使用共享缓存**

把内存缓存换成 Redis 或文件缓存，让多个 Worker 共享同一份缓存。但引入 Redis 对单人项目来说太重了。

## 6. 经验教训

### 6.1 技术层面

**教训 1：内存缓存 + 多进程 = 隐蔽的陷阱**

`_day_metrics_cache` 的设计意图是好的（加速历史日期查询），但它假设了整个应用只有一个进程。在单进程环境下它工作完美，但一旦引入多 Worker，它就变成了缓存不一致的源头。这个 bug 潜伏了很久，因为：
- 正常打卡都是"今天"，不走缓存
- 历史日期补打卡是低频操作
- 用户很少会"来回切换日期"来对比同一日的不同结果

**教训 2：SQLite 与多进程的天然冲突**

SQLite 的文件级锁机制决定了它不适合高并发写入场景。本项目虽然并发低，但多 Worker + 内存缓存的组合仍然制造了"一个进程写了数据库，另一个进程不知道"的问题。如果未来业务复杂化，应该优先考虑 PostgreSQL + 共享缓存（Redis）的架构。

**教训 3：Fallback 逻辑的边界意识**

`_build_shift_intervals` 中推断失败时的 fallback `intervals.append((pending_start_dt, event_dt))` 在设计时应该考虑"event_dt 可能是几天后的下一个 clock_in"。跨天区间的产生是合理的（如 23:00→02:00），但跨天区间不应该覆盖"中间完全没有打卡记录的整天"。

### 6.2 排查层面

**教训 4：不要只查容器数量，要查进程数量**

最初排查时曾误以为"只有一个 Docker 容器"就代表单进程。实际上 `docker ps` 看到的只是容器层面，容器内部的进程结构（Gunicorn Worker 数）才是决定缓存一致性的关键。今后遇到"数据偶尔对偶尔不对"的问题，第一时间应该怀疑：
- 是否有多个 Worker？
- 是否有内存缓存？
- 写入操作是否只清除了当前进程的缓存？

**教训 5：API 验证是定位分布式/并发问题的金标准**

前端交替显示可能是浏览器缓存、前端状态管理、或服务端问题。通过命令行连续请求同一 API，如果 API 本身也返回不同结果，就可以 100% 排除前端，锁定服务端。

### 6.3 运维层面

**教训 6：修改历史数据后必须考虑缓存失效范围**

通过 API 或 CLI 修改历史数据时，如果系统有内存缓存，必须确认：
- 被修改日期的缓存是否被清除？
- 依赖该日期的其他日期缓存是否也需要清除？（如本例中 5月1日 的修改影响了 5月2日的计算结果）
- 多进程环境下，如何让所有进程的缓存都失效？

**教训 7：个人项目也要重视架构文档**

本项目是 vibe coding 出来的，很多设计决策（如为什么用 `-w 2`、为什么加 `_day_metrics_cache`）没有留下记录。当出现问题时，需要重新阅读代码才能理解当初的意图。建议在关键配置处添加注释，说明设计决策和已知限制。

### 6.4 决策层面

**教训 8：不要为了"可能的高并发"过早引入复杂度**

`-w 2` 的设定可能是出于"万一并发高了怎么办"的预防心理。但对于一个单人使用的工具，单 Worker 完全够用。过早引入多 Worker 带来了缓存不一致的问题，收益却几乎为零。

**教训 9：修复方案要和用户的使用习惯匹配**

在讨论修复时，曾提出过"放宽首个 gap 检查"和"限制 fallback 到当天"两种方案。但用户指出这会破坏跨天识别能力。最终方案没有修改任何代码，而是通过补人工打卡 + 重启容器解决。这说明：**理解用户的实际使用场景比技术完美主义更重要**。
