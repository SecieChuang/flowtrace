# Flowtrace 混乱打卡核查 CLI 使用指南

## 功能说明

本工具用于核查和修复考勤系统中的"混乱打卡"数据。检测引擎（V4，槽位约束）先按活动记录构造跨日连续的**活跃段**，每个活跃段有两个槽位：段首要一张上班卡，段尾要一张下班卡。槽位状态异常即触发检测，共三类问题：

| 类别 | 子类 | 界面文案 | 含义 | 推荐操作 |
|------|------|----------|------|----------|
| `slot_mismatch` | `head_far` | 打卡距段首较远 | 段首槽找到上班卡，但距离超过正常阈值（仍在 1.5× 阈值内） | 保留这条（距离可接受） |
| `slot_mismatch` | `tail_far` | 打卡距段尾较远 | 段尾槽找到下班卡，距离同上 | 保留这条（距离可接受） |
| `slot_mismatch` | `head_wrong_dir` | 段首方向错误 | 段首槽找到的是下班卡，疑似打反 | 翻转方向（下班 → 上班） |
| `slot_mismatch` | `tail_wrong_dir` | 段尾方向错误 | 段尾槽找到的是上班卡，疑似打反 | 翻转方向（上班 → 下班） |
| `missing_checkin` | `head_empty` | 缺少上班打卡 | 段首槽空 | 按推断值补一条上班卡 |
| `missing_checkin` | `tail_empty` | 缺少下班打卡 | 段尾槽空（进行中的段不报） | 按推断值补一条下班卡 |
| `isolated` | — | 孤立打卡 | 打卡未被任何活跃段的槽位收纳（含"打完卡去开会一整天"的场景） | 删除，或按情况保留 |

> 设计原则：打卡是事实信号，算法只"建议"，所有修改都需要你确认后才执行。槽位规则与判定阈值的完整设计见 [clock-detection-architecture-final.md](clock-detection-architecture-final.md)。

## 运行方式

### 日常入口（推荐）：编号菜单

```bash
# 仓库根目录，进入编号菜单（查看/修复/单日诊断/自选范围）
sh manage.sh
# 或直接进容器
docker exec -it flowtrace-server python manage_cli.py
```

菜单选项：

```
1. 查看默认范围的问题        （只列出，不修改）
2. 修复默认范围的问题        （进入交互式修复流程）
3. 查看某一天的诊断          （打卡、活动段、涉及的问题）
4. 自选天数后查看问题
5. 自选天数后进入修复
q. 退出
```

### 命令行参数（脚本/维护用）

```bash
# Docker 容器内（推荐）
docker exec -it flowtrace-server python manage_cli.py --days 7          # 最近 7 天
docker exec -it flowtrace-server python manage_cli.py --from 2026-04-01 --to 2026-04-30
docker exec -it flowtrace-server python manage_cli.py --list --days 30  # 只列出问题，不修改
docker exec -it flowtrace-server python manage_cli.py --inspect --date 2026-04-20  # 单日诊断

# 本地开发（包模式，仓库根目录）
python -m server.manage_cli --days 7
```

- 无参数时进入编号菜单
- 默认扫描天数由服务端配置中的 `manage_default_days` 控制（默认 30 天，见 [configuration.md](configuration.md)）
- 扫描区间为所选范围 ±1 天缓冲：缓冲区只参与活跃段构造与槽位搜索，不会产生问题报告

## 交互修复流程

### 1. 问题展示

每条检测到的问题会显示：

```
══════════════════════════════════════════════════════════════════════
[1/3]  段首方向错误  ·  2026-04-20
       09:00:30 下  (无配对)

       当日打卡 (2 条):
         09:00:30 下  ←
         18:02:00 下

       参考活动段:
         08:50:00–12:10:00
         13:30:00–18:05:00

怎么处理？
  [1] 将 09:00:30 这条翻转为上班  ← 推荐
  [2] 删除 09:00:30 这条
  [3] 修改时间
  [s] 跳过
  [b] 返回上一条
  [q] 退出
```

缺卡类问题没有对应打卡，锚点显示推断时间：

```
[2/3]  缺少下班打卡  ·  2026-04-21
       2026-04-21 18:05:00（待补卡）  (缺失打卡)
       ...
  [1] 补一条 18:05:00 的下班（推断值）  ← 推荐
  [2] 手动补一条下班
  [s] 跳过
```

- **标题行**：问题类型（界面文案）和日期
- **当日打卡**：该日所有打卡记录，`←` 标记为本次涉及的打卡
- **参考活动段**：该日的活动记录（如有），供参考
- **推荐操作**：`← 推荐` 标记在推荐项后

### 2. 选择操作

输入数字选择操作；`s` 跳过当前问题；`b` 返回上一条重新选择（会撤销已选的操作）；`q` 退出（不会做任何修改）。

部分操作需要补充输入（如修改时间时输入 `HH:MM:SS`，格式无效可重试 3 次后取消该操作）。

### 3. 汇总确认

所有问题处理完后，会列出全部待执行操作：

```
待执行操作汇总：

  [1] 将 09:00:30 这条翻转为上班
  [2] 补一条 18:05:00 的下班（推断值）
  [3] 跳过

确认执行？(回车确认，其他键取消):
```

**按回车才执行**，输入其他任意键取消（取消后不会有任何修改）。

### 4. 批量执行

确认后按顺序批量执行，逐条报告结果：

```
  ✓ 将 09:00:30 这条翻转为上班
  ✓ 补一条 18:05:00 的下班（推断值）

✓ 完成。已执行 2 条，跳过 1 条。
```

## 各类问题的操作选项

### 距离较远（`head_far` / `tail_far`）

| 操作 | 说明 |
|------|------|
| 保留这条 | 距离可疑但可接受，不做修改（推荐；保护"在岗但离开电脑"等真实场景） |
| 删除 | 删除该条打卡 |
| 修改时间 | 修改该条打卡的时间 |

### 方向错误（`head_wrong_dir` / `tail_wrong_dir`）

| 操作 | 说明 |
|------|------|
| 翻转方向 | 将该条翻转为上班/下班（推荐） |
| 删除 | 删除该条打卡 |
| 修改时间 | 修改该条打卡的时间 |

### 缺少打卡（`head_empty` / `tail_empty`）

| 操作 | 说明 |
|------|------|
| 补一条（推断值） | 按活跃段端点推断的时间自动补录（推荐，有推断值时出现） |
| 手动补一条 | 手动输入补卡时间 |

### 孤立打卡（`isolated`）

| 操作 | 说明 |
|------|------|
| 删除 | 删除该条孤立打卡（推荐） |
| 手动补一条配对卡 | 补一条相反方向的打卡使其成对 |
| 修改时间 | 修改该条打卡的时间 |
| 保留 | 不做修改（如"开会一整天"等无活动但打卡正确的场景） |

## 单日诊断（--inspect）

展示指定日期的打卡明细、活动段，以及涉及该日期的所有问题（只读，不修改）：

```
Inspect 2026-04-20

Checkins:
  #12 09:00:30 clock_out created=2026-04-20 09:00:31
  ...

Activity slices:
  08:50:00 - 12:10:00  200m  auto
  ...

Detected issues touching this date:
  [1] slot_mismatch-12 | 段首方向错误 | 2026-04-20 | 2026-04-20 09:00:30 下#12 | recommended: 将 09:00:30 这条翻转为上班
```

## 注意事项

- 操作会直接写入数据库，建议在操作前备份数据（`cp data/flowtrace.db data/flowtrace-$(date +%F).db.bak`）
- 跳过的问题不会被处理，下次运行时仍会出现
- 程序中断（Ctrl+C）时，已执行的操作不会回滚；汇总确认前的中断不会做任何修改
- 修复落库后会自动失效对应日期的日指标缓存；当前服务端为单 worker 部署，一般无需重启容器（背景见 [incident-2026-05-01-cache-inconsistency.md](incident-2026-05-01-cache-inconsistency.md)）
